# [파트 2] 0-Line 영역 검출

3D 스캔 편차 히트맵에서 **편차가 0 근처인 영역**을 찾아 마스크로 뽑아낸다.
보정시트에서 `0` 으로 표기되는, 금형을 깎지도 붙이지도 않는 구간이다.

## 왜 "초록색 = 0" 으로는 안 되는가

처음에는 HSV 초록 대역(Hue 45~85)을 고정 임계값으로 잡는 방법을 썼다.
실제 스캔 이미지 3장을 확인해 보니 그 방법으로는 한 장도 제대로 처리되지 않는다.

| 이미지 | 컬러바 위치 | 방향 | 범위 |
|---|---|---|---|
| `JD_67XX6-DR000` | **좌측** | 180° 회전됨 | −3.00 ~ +3.00 |
| `JD_64XX2-DR000` | **좌측** | 180° 회전됨 | **−1.50 ~ +2.00 (잘림)** |
| `JD_71XX2-DR000` | **우측** | 정상 | −2.00 ~ +2.00 |

문제가 세 가지다.

1. **범위가 이미지마다 다르다.** ±3.0 짜리와 ±2.0 짜리에서 같은 초록색이 서로 다른
   편차를 뜻한다.
2. **컬러바가 잘린 경우가 있다.** `JD_64XX2` 는 위가 잘려 −1.50 ~ +2.00 의 비대칭
   범위다. 이 경우 0 은 컬러바 중앙이 아니라 아래에서 42.9% 지점이다.
3. **3D 렌더링 음영이 있다.** 같은 편차라도 면이 기울면 어두워진다.
   고정 밝기·채도 임계값에 걸리지 않는다.

### 해결 방법

**이미지 안에 있는 컬러바를 매번 읽어서 색→값 대응표를 새로 만든다.**
사람이 범례를 보고 판독하는 것과 같다.

```
컬러바 검출 → 색상 순서로 방향 판별 → 색상(Hue)으로 픽셀값 역산 → |값| ≤ 허용오차
```

- 컬러바 위치·방향은 **자동 판별**한다. 좌/우 어디든, 180° 회전돼 있어도 된다.
  무지개 램프는 Hue 가 단조 변하므로(마젠타 150 → 빨강 0), 양 끝 Hue 를 비교하면
  어느 쪽이 음수인지 알 수 있다. OCR 이 필요 없다.
- **밝기를 빼고 색상만** 본다. 3D 음영에 흔들리지 않는다.
- 컬러바가 잘려도 **자동으로 보정한다.** 아래 참고.

### 잘린 컬러바 자동 보정

`JD_64XX2` 는 컬러바 위가 잘려 −1.50 ~ +2.00 의 비대칭 범위다.
이 경우 편차 0 은 컬러바 중앙이 아니다.

보이는 색이 **정식 무지개 램프의 어느 구간인지** 되짚으면 0 위치를 계산할 수 있다.
정식 램프는 마젠타에서 빨강까지이고, GOM 출력은 대칭 범위(±V)를 쓰므로
편차 0 은 항상 정식 램프의 정중앙이다. 보이는 구간이 램프의 11.2~99.3% 라면
0 은 보이는 구간의 `(50 − 11.2) / (99.3 − 11.2) = 44.0%` 지점이다.

| 이미지 | 보이는 구간 | 0 위치 (자동) | 0 위치 (실제) | 오차 |
|---|---|---|---|---|
| `JD_64XX2` | 11.2 ~ 99.3% | 44.0% | 42.9% | 1.1%p |
| `JD_67XX6` | 0.8 ~ 99.3% | 50.0% | 50.0% | 0.0%p |
| `JD_71XX2` | 0.8 ~ 99.3% | 50.0% | 50.0% | 0.0%p |

사람이 `--vmin/--vmax` 를 직접 넣은 결과와 비교하면 **부호 경계선은 세 장 모두
픽셀 하나까지 동일하다** (16,447 / 11,075 / 11,001 px, 다른 픽셀 0개).
0 영역(면)은 64XX2 에서 IoU 0.804, 나머지는 0.97 이상이다.

즉 **`--vmin/--vmax` 없이도 0-Line 검출은 그대로 된다.**
mm 단위 수치가 필요할 때만 값을 넣으면 된다.

```bash
python -m zero_line_detection.run --input "data/intermediate/JD_64XX2-DR000 3D 스캔.png" --vmin -1.5 --vmax 2.0
```

## 0-Line "선" 과 0 "영역" 은 다르다

이 모듈은 두 가지를 따로 낸다. 섞으면 안 된다.

| | 무엇 | 임계값 | 성격 |
|---|---|---|---|
| **0-Line (선)** | 편차가 + 에서 − 로 **부호가 바뀌는 경계** | **없음** | 계산된 사실 |
| **0 영역 (면)** | `|편차| ≤ 허용오차` | 필요 | 사람의 판단 |

부호가 바뀌는 지점은 정의상 편차가 정확히 0인 곳이므로 **임계값을 하나도 쓰지 않는다.**
누가 계산해도 같은 결과가 나온다. 반면 "0 근처" 를 어디까지로 볼지는 값을 정해야 하고,
그 값은 현장이 정할 문제지 우리가 정할 문제가 아니다.

`zero_line_overlay.png` 는 둘을 함께 그린다.

- **검은 선** = 부호 경계. 허용오차를 바꿔도 움직이지 않는다.
- **마젠타 면** = 0 영역. 허용오차에 따라 넓어지고 좁아진다.

### 허용오차가 결과를 얼마나 좌우하는가

`zero_line_tolerance_sweep.csv` 에 민감도가 기록된다. `JD_71XX2` 기준:

| 허용오차 | 0 영역 면적 | 부품 대비 |
|---|---|---|
| ±0.04 mm | 14,773 px | 8.8% |
| ±0.10 mm | 28,587 px | 17.0% |
| ±0.20 mm | 52,799 px | 31.5% |
| ±0.30 mm | 73,001 px | 43.5% |
| ±0.40 mm | 89,940 px | 53.6% |
| ±0.60 mm | 115,117 px | 68.6% |

**8.8% 에서 68.6% 까지 벌어진다.** 임계값 하나로 결론이 8배 달라지므로,
이 값을 조용히 정해두고 결과만 내놓으면 근거를 댈 수 없다.
그래서 기본값을 쓰되 민감도 표를 함께 내고, 부호 경계선은 임계값과 무관하게 따로 낸다.

같은 부호 경계선이 나오는지 직접 확인할 수 있다.

```bash
python -m zero_line_detection.run --input "data/intermediate/JD_71XX2-DR000 3D 스캔.png" --vmin -2.0 --vmax 2.0 --tolerance 0.1
```

```bash
python -m zero_line_detection.run --input "data/intermediate/JD_71XX2-DR000 3D 스캔.png" --vmin -2.0 --vmax 2.0 --tolerance 0.4
```

두 번 모두 `zero_line_crossing.png` 는 11,001 px 로 동일하다.

## 제로라인 — "0색" 과 "기준" 은 다르다

지금까지 낸 0 영역은 편차가 0에 가까운 **색**을 모은 것이었다. 그런데 스프링백
관점에서 제로라인은 다른 것이다.

성형 후 하중을 빼면 부품이 통째로 움직이는 게 아니라, **거의 움직이지 않는
부분을 축으로 나머지가 돌아간다.** 그 안 움직이는 부분이 제로라인이고,
보정량을 재는 기준이 된다. 넓으면 기준 **면**, 좁고 길면 기준 **선** 이 된다.

문제는 "편차가 0에 가까운 색" 만으로는 이걸 특정할 수 없다는 것이다.
편차가 0을 스치듯 지나가는 곳(기울기가 큰 곳)은 측정 위치가 몇 mm만 틀어져도
값이 확 달라져서 기준이 될 수 없다. 계측에서 데이텀을 평평한 면에 잡는 것과
같은 이유로, **편차가 0이고 동시에 주변이 평탄한 곳**만 후보로 남긴다.

```python
from zero_line_detection.zero_criteria import find_zero_candidates

candidates, flat, gradient = find_zero_candidates(
    out.values, out.part_mask, tolerance=out.result.tolerance,
)
```

각 후보는 형태로 `plateau`(면, 길쭉함<3) 또는 `ridge`(선, 길쭉함≥3) 로 나뉘고,
0 근접도·평탄도·크기를 합친 점수를 받는다. `JD_71XX2` 기준 색만으로 잡은
53,047px 중 22,355px 만 평탄 조건까지 통과했다.

**남은 문제 — 기울기 문턱값(하위 40%)은 여전히 우리가 정한 값이다.**
"편차 0" 과 "제로라인" 이 다르다는 방향은 스프링백 원리로 근거가 있지만,
정확히 몇 % 를 평탄으로 볼지는 현장 확인이 필요하다.
→ `06_회의록/아진산업_방문_준비_20260825.md` Q1

## 다각형 정리 — 톱니 경계를 깔끔하게

픽셀 마스크의 경계는 톱니처럼 너덜너덜하다. 가장 큰 영역이 면적 47,574px 에
둘레 5,128px 였다(매끈한 도형이면 800px 면 충분하다). 닫기·열기 연산으로
다듬고 Douglas-Peucker 로 꼭짓점을 줄인다. 가늘고 긴 0 영역은 외곽선만
따르면 안쪽 빈 공간까지 칠해지므로, 구멍(내부 윤곽)을 함께 살린다.

```python
from zero_line_detection.polygonize import polygonize, draw_polygons

polys = polygonize(out.mask, preset="balanced")   # accurate / balanced / clean
img = draw_polygons(rgb, polys)
```

| 프리셋 | 꼭짓점 | 원본 대비 IoU | 용도 |
|---|---|---|---|
| `accurate` | 1,073 | 0.86 | 수치를 뽑아 쓸 때 |
| **`balanced`** | **850** | **0.78** | **기본 · 화면 표시** |
| `clean` | 256 | 0.53 | 발표·외주 전달 (모양은 크게 뭉개짐) |

원본은 조각 11개에 꼭짓점 2,911개였다. 모양 보존과 단순함은 맞바꾸는
관계이므로 용도에 맞는 프리셋을 고른다.

## 정확도

합성 이미지는 편차 분포를 우리가 정했으므로 **정답을 안다.**
실제 스캔으로는 불가능한 정량 검증이 가능하다.

```bash
python -m zero_line_detection.make_sample --evaluate
```

| 지표 | 값 |
|---|---|
| IoU | **0.914** |
| 정밀도 | **0.998** |
| 재현율 | 0.916 |

정밀도가 거의 1.0 이라는 것은 **0이 아닌 곳을 0이라고 하는 일이 거의 없다**는 뜻이다.
재현율이 0.92 인 것은 라벨 박스·지시선에 가려진 부분을 제외하기 때문이며,
파트 4의 `clean_deviation_map.png` 가 들어오면 올라간다.

### 실제 스캔 검증 ★

합성 IoU 는 내가 만든 정답에 대한 점수라 자기 채점에 가깝다.
그런데 스캔 이미지에는 **사람이 적어 둔 정답이 이미 들어 있다.**

```
[-1.7] ──────────● 이 지점의 편차는 -1.7 이다
```

라벨 박스와 지시선 끝점을 자동으로 찾고, 그 지점의 색을 편차값으로 되읽어
라벨 값과 비교했다. `JD_71XX2` 의 22개 지점 기준:

| 지표 | 값 |
|---|---|
| MAE | **0.085 mm** |
| RMSE | 0.199 mm |
| 상관계수 | **0.9839** |
| 0.2mm 이내 | 20 / 22 (91%) |

오차의 출처를 나눠 보면 색 판독 자체는 더 정확하다.

| 구분 | 개수 | MAE |
|---|---|---|
| 지시선이 교차해 앵커를 잘못 잡은 것 | 2 | 0.57 mm |
| **나머지 (앵커가 정상)** | **20** | **0.036 mm** (최대 0.108) |

라벨 종류별로도 갈린다.

| 라벨 | 값 범위 | 개수 | MAE |
|---|---|---|---|
| 흰색 (0 근처) | −0.5 ~ 0.0 | 13 | **0.041 mm** |
| 빨강 (큰 편차) | −2.0 ~ +1.7 | 9 | 0.147 mm |

**0-Line 검출에 직접 쓰이는 0 근처 구간이 가장 정확하다** (0.041mm).
큰 편차 쪽 오차가 큰 것은 그 지점들이 부품 가장자리·급경사면에 몰려 있어
앵커 위치가 조금만 어긋나도 값이 크게 변하기 때문이다.

실행 방법 (숫자 읽는 OCR 은 파트 3 담당이라 값은 사람이 넣는다):

```bash
python -m zero_line_detection.validate_real --image "data/intermediate/JD_71XX2-DR000 3D 스캔.png" --emit-template
```

```bash
python -m zero_line_detection.validate_real --image "data/intermediate/JD_71XX2-DR000 3D 스캔.png" --truth data/truth_71XX2.csv --vmin -2.0 --vmax 2.0
```

### 자체 점검

한 장짜리 IoU 하나로는 부족하다. 현실적인 변형을 넣어 13가지를 확인한다.

```bash
python -m zero_line_detection.selftest
```

| 항목 | 결과 |
|---|---|
| 여러 시드 5장 | 평균 0.910, 최저 0.876 |
| 크기 0.5 ~ 2.0배 | 0.874 ~ 0.932 |
| JPEG 품질 95 ~ 40 | 0.901 ~ 0.943 |
| 180° 회전 | 0.914, 컬러바 방향 자동 판별 |
| 부호 경계선 불변성 | 허용오차 0.1↔0.4 에서 선 동일, 면만 4배 변화 |
| 잘린 컬러바 감지 | 감지 후 경고 |

크기 변경 항목은 실제로 버그를 잡아낸 검사다. 컬러바 가장자리가 배경과 섞이면
(축소·확대·화면 캡처에서 반드시 생긴다) 균일도 검사에 걸려 컬러바를 통째로
놓쳤다. 양옆을 잘라내고 안쪽만 보도록 고쳤다.

### 라벨과 지시선을 따로 지우는 이유

흰 배경·회색 미측정면·검은 글씨는 컬러바에 없는 색이라 자동으로 걸러진다.
그런데 **빨간 라벨 박스와 파란 지시선은 컬러바에 실제로 있는 색**이다
(빨강=최댓값, 파랑=음수). 지우지 않으면 라벨이 통째로 "편차 +3.0 영역" 으로 오인된다.
그래서 색이 아니라 **형태**로 구분한다 — 라벨은 작고 사각형이며 안에 흰 글씨가 있고,
지시선은 얇다.

## 주요 옵션

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--input` | 자동 탐색 | 입력 이미지 |

| `--vmin`, `--vmax` | 없음 | 컬러바 최소·최대값. mm 단위가 필요할 때만 |

| `--morph-close` | `4` | 끊긴 영역 연결 강도 |
| `--no-annotation-mask` | — | 자체 라벨 제거 끄기 (파트 4 결과 사용 시) |

| `--all-samples` | — | `data/sample` 일괄 처리 |

## 알려진 한계

### 1. 스캔의 0 영역 ≠ 보정시트의 `"0" 라인`

`JD_67XX6` 은 스캔과 보정시트가 모두 있어 대조해 봤다.
검출된 0 영역과 시트의 빨간 점선 `"0" 라인` 구간은 **대체로 겹치지만 완전히 같지는 않다.**

시트의 `0` 은 "편차가 0이다" 가 아니라 **"작업자가 이 구간은 손대지 않기로 판단했다"** 에
가깝다. 편차가 0인 곳은 자연히 유지 대상이 되지만, 편차가 있어도 후공정이나 부위 중요도를
고려해 유지하기도 한다.

**이 모듈은 스캔에서 편차 0인 영역을 찾는 것까지만 한다.**
그것이 시트의 `0` 이 되는지는 멘토 확인이 필요하다. → `docs/input-output-contract.md` §6

### 2. 잘린 컬러바 보정은 "정식 램프가 대칭 범위" 라는 가정에 기댄다

실제 스캔 3장에서는 모두 성립했다 (±3.0 / ±2.0 / 잘린 것도 역산하면 ±2.02).
GOM 출력의 관례로 보이지만, 비대칭 범위로 내보낸 이미지가 들어오면 틀린다.
그런 경우 `--vmin/--vmax` 로 직접 지정해야 하며, 지금은 이를 감지할 방법이 없다.

### 3. 0 "영역" 의 허용오차는 아직 우리가 정한 값이다

기본값 "컬러바 반경의 10%" 는 근거 있는 추정이지 현장 기준이 아니다.
시트에서 `0` 과 `-0.5` 가 구분되는 것으로 보아 그 사이 어딘가인데, 정확한 값은 확인이 필요하다.

다만 이 한계는 **0 영역(면)에만 해당한다.** 부호 경계선은 임계값을 쓰지 않으므로
현장 기준이 확정되기 전에도 그대로 쓸 수 있다.
현장 값이 확인되면 `--tolerance` 로 고정하면 되고, 그때까지는 민감도 표
(`zero_line_tolerance_sweep.csv`)를 근거 자료로 첨부한다.

### 4. 축척을 모른다

픽셀↔mm 변환이 없다. 영역 면적은 `px` 단위로만 낸다.
CAD 파일이 확보되면 축척을 넣어 `mm²` 로 바꿀 수 있다.

### 5. 세선화(`--centerline`)는 느리다

Zhang-Suen 세선화는 순수 파이썬 반복이라 2400x1520 이미지에서 21초쯤 걸린다.
기본값은 꺼져 있고, 선 형태가 필요하면 거의 공짜인 `zero_line_crossing.png`
(부호 경계선)를 먼저 쓴다. 중심선이 꼭 필요하면 `--centerline` 을 준다.

### 6. 컬러바가 없는 이미지는 처리 불가

`detect_colorbar` 가 실패하면 에러를 낸다. 색→값 대응의 유일한 근거이므로,
컬러바가 잘린 이미지를 만들지 말 것을 파트 4에 요청해 두었다.

## 성능

1688x1016 실제 스캔 기준 약 1.2초, 합성 1200x760 기준 약 0.5초.
`--centerline` 을 켜면 이미지 크기에 따라 2~20초가 추가된다.
