# 제로라인 학습 로드맵 — 지금 된 것 / 안 된 것 / 필요한 것

`README_zero_points.md` 가 "왜 라벨 실측값 방식인가"를 설명한다면, 이 문서는
"학습(ML)까지 가려면 뭐가 있고 뭐가 없는가"를 정리한다.

## 원칙 (반복 확인됨)

시트 좌표는 **정답(label)** 으로만 쓴다. 모델 입력(feature)은 3D스캔
실측값에서만 뽑는다 — 컬러바 색, 편차 포인트 값, 그 값들의 공간적 분포.
"선이냐 면이냐"도 규칙으로 정하지 않고 학습 대상으로 남겨둔다. (현업 확인
2026-08-25, 재확인 2026-08-25)

## 완료 — 지금 데이터(부품 3개)로 할 수 있었던 것

1. **JD_71XX2 보정시트 등록** — 파일명이 다른 두 부품과 달리
   `JD_71XX2-DR000 보정 시트.png`(중간에 띄어쓰기)라 이전엔 자동 등록이
   조용히 실패해 있었다. 파일명 확인 후 등록 완료 — `areas`(존 5개),
   좌우반전. `zero_line_library.json` 에 반영됨.

2. **후보 라벨링 파이프라인** (`ml_dataset.py`) — my_lab이 뽑은 0포인트
   후보마다 보정시트 정답과의 거리를 재서 양성/음성 라벨을 자동으로
   붙인다. 특징은 |편차|(3단계 스무딩), 기울기(3단계), 부호경계까지
   거리, 부품테두리까지 거리, 국소표준편차, 기존 규칙의 강도값 — 전부
   스캔에서만 계산. 시트 좌표는 라벨을 매기는 데만 쓰고 특징에는 안 넣음.

   허용오차(`tolerance_px=45`)는 실측으로 골랐다 — 후보-정답 거리를
   재보면 3부품 모두에서 진짜 근처(5~35px)와 완전히 딴 곳(80px 이상)
   사이에 뚜렷한 틈이 있었다.

   결과: 총 38개 후보(양성 13 / 음성 25) → `ml_data/candidate_dataset.csv`

3. **학습·검증 하네스** (`train_zero_classifier.py`) — scikit-learn 없이
   numpy 로지스틱회귀(L2 정규화) + leave-one-part-out 검증. AUC는
   순위-합 공식으로 직접 계산(scipy만 사용). 최종 가중치는
   `ml_data/classifier_weights.json` 에 저장만 하고 **서버에는 연결
   안 함**.

### 스모크테스트 결과 (참고용 — 통계적으로 못 믿음)

| held-out 부품 | 후보 수 (양성) | AUC | TP | FP | FN | TN |
|---|---|---|---|---|---|---|
| 64XX2 | 12 (4) | 0.56 | 2 | 2 | 2 | 6 |
| 67XX6 | 18 (7) | 0.75 | 2 | 0 | 5 | 11 |
| 71XX2 | 8 (2) | 0.67 | 0 | 1 | 2 | 5 |

3개 중 2개 폴드에서 AUC가 0.5(무작위)보다 뚜렷이 높다 — `feature_study.py`
에서 확인한 "신호는 있다"는 결론과 방향은 맞는다. 다만 폴드당 표본이
8~18개뿐이라 이 숫자 자체를 근거로 쓰면 안 된다. **코드가 도는지
확인하는 용도일 뿐이다.**

## 아직 안 된 것 + 필요한 것

| 안 된 것 | 왜 안 되는가 | 필요한 것 |
|---|---|---|
| **선/면(line vs zone) 판단 학습** | 부품 단위 라벨이 3개뿐(64=line, 67=area, 71=area) — 이진분류를 학습할 최소 표본조차 안 됨 | 부품 다양성 확대. line/area 각각 최소 5개 이상, 즉 부품 10개 이상 |
| **신뢰할 수 있는 성능 지표** | leave-one-part-out 폴드당 후보 8~18개라 우연 변동이 큼 (위 표) | 부품 15~20개 이상. `train_zero_classifier.py` 의 `MIN_PARTS_TO_TRUST` 로 이미 게이트해둠 |
| **프로덕션 랭킹에 모델 점수 반영** | n=3 모델이 지금 규칙(`connect_strongest_pair`)보다 못할 가능성이 높음 | 위 두 항목이 먼저 해결돼야 함. 그 전엔 가중치 파일만 쌓아두고 서버엔 안 붙임 |
| **선/면 형태 불일치 (새로 확인, 아래 참고)** | `areas`(존)로 표기된 부품도 지금은 무조건 점 2개를 잇는 "선"으로만 출력됨 | 아래 "다음 실행 항목" 참고 |
| **새 사례 반영 자동화** | 새 부품이 들어올 때마다 `my_lab` 4단계 수동 실행 → `zero_points_data/<품번>.json` 수동 배치 → `register_sheet.py` 수동 등록 → `ml_dataset.py`/`train_zero_classifier.py` 수동 재실행 | 이 네 단계를 묶는 파이프라인 스크립트. 지금은 부품 3개라 수동으로도 충분하지만 10개 이상 들어오면 병목이 됨 |

## 프로덕션 파이프라인 채점 (`evaluate_pipeline.py`, 신규)

데이터가 더 안 늘어도 계속 쓸 수 있는 것 — server.py 가 실제로 쓰는 경로
(`cluster_zero_points` → `connect_strongest_pair`)를 그대로 재현해서
보정시트 정답과 대조한다. 규칙을 고칠 때마다 이 스크립트를 다시 돌려서
"진짜 나아졌는지" 확인한다.

| 품번 | 정답 종류 | 선→정답 중앙값% | 정답→선 중앙값% | 끝점 오차%(2개) |
|---|---|---|---|---|
| 64XX2 | line | 4.29 | 5.37 | 2.9 / 2.1 |
| 67XX6 | areas | 5.31 | 19.34 | 11.6 / 3.3 |
| 71XX2 | areas | 2.32 | 41.05 | 2.3 / 6.0 |

**정정**: 이전에 이 문서와 README에 "JD_64XX2 진짜 끝점이 강도 순위
6위·3위라 못 맞춘다"고 적었던 건 마스크 근접 필터링을 넣기 *전* 상태
기준이었다. 지금 다시 재보니 끝점 오차가 대각선 대비 2~6% 수준으로
꽤 준수하다 — 그 문제는 이미 해결된 상태였다. 낡은 정보를 근거로 계속
쓸 뻔했다.

**진짜 남은 문제**: `areas`(존)로 표기된 두 부품(67XX6, 71XX2)은 정답→선
커버리지가 19%, 41%로 나쁘다. 이유는 명확하다 — 정답이 여러 존(9개,
5개)으로 흩어져 있는데 지금 로직은 무조건 점 2개만 이어서 "선" 하나로
만든다. 존이 여러 개인 부품엔 애초에 선이라는 출력 형태 자체가 안 맞는다.

### 다음 실행 항목

`cluster_zero_points()` 가 이미 각 군집을 `point`/`zone` 으로 구분해서
낸다 — 즉 "존이 여러 개 흩어져 있다"는 신호는 지금도 갖고 있다. 다음
개선은 이렇다: 강한 군집이 여러 개고 서로 멀리 흩어져 있으면(예: 상위
N개 군집의 위치 분산이 크면) 점 2개를 억지로 잇지 않고 **군집들을 그대로
존으로 보여준다.** 시트가 선인지 존인지 미리 알아야 하는 게 아니라,
스캔에서 나온 군집 형태 자체로 판단하는 것이라 시트 베끼기가 아니다.
이건 데이터가 더 없어도 지금 3부품으로 바로 검증 가능 — 아직 구현
전이며, 화면에 기본으로 보이는 결과가 바뀌는 변경이라 적용 전에 확인
받는다.

## 3D 데이터 경로 (`cad_import/`, 신규)

현업 자료(2026-08-25)를 받아 확인한 결과, 제로라인 판정 4가지 방법 중
우리가 쓰던 건 **3번(컬러맵 제로존) 하나뿐**이었다. 나머지 3개는 전부
3D 데이터가 필요하다. 부품별 우선순위(선루프=가이드레일 중심선·조립 홀,
대시보드=차량 센터 Y0·크로스멤버 마운트)를 보면 제로라인 기준이 결국
**조립 기준 좌표**에서 나오는데, 이건 편차 히트맵 색에 없는 정보다.

그래서 STEP/STL 을 읽어 형상과 **조립 홀 좌표**를 뽑는 경로를 만들었다.
`cad_import/README.md` 에 근거와 검증 결과가 있다.

- CATIA 네이티브(.CATPart)는 CGM 독자 포맷이라 못 읽는다(실측 확인).
  현업에 **STEP(AP214)** 내보내기를 요청해야 한다.
- STEP 이면 홀 지름·중심·축을 정확히 복원한다(테스트 7건 통과).
  STL 이면 형상만 — 삼각망으로 내보낸 시점에 홀 정보가 사라진다.
- UI 사이드바 **3D 데이터** 탭에서 바로 열어볼 수 있다.

**아직 RPS 정렬 자체는 없다.** CAD 쪽 절반만 열렸고, 정렬하려면 *같은
부품의 3D 스캔*(STL/PLY/점군)이 필요한데 현재 스캔은 전부 2D 히트맵
PNG 다. 즉 요청할 데이터가 두 가지로 늘었다:

1. **CAD**: STEP(AP214) — CATPart 말고
2. **3D 스캔 원본**: STL/PLY/점군 — 히트맵 이미지 말고

이 둘이 같은 부품으로 짝을 이뤄 오면 1·2·4번 방법이 전부 열린다.

## 보정치-실측값 diff 데이터셋 (`correction_dataset.py`, 신규)

보정시트에는 제로라인 말고도 부품 곳곳에 **실제 보정치 숫자**가 콜아웃
박스로 찍혀 있다(예: "-0.4"). 같은 위치의 스캔 실측 편차값과 비교하면
"측정값을 그대로 뒤집은 것과 실제 보정치가 얼마나 다른지"를 배울 수
있다 — 이게 residual(잔차) 이다.

- `sheet_values.py`: 콜아웃 박스(흰 바탕+검은 글자)와 빨간 점(측정
  지점)을 검출한다. 박스 테두리가 너무 옅어(실측 확인) 테두리 대신
  **글자 자체**로 콜아웃을 찾고, 점과 리더선이 픽셀상 맞닿아 있어서
  모폴로지 열기로 선을 지우고 점만 남기는 방법을 썼다.
- `POST /api/sheet-values`: 콜아웃을 VLM(Qwen)으로 읽는다. server.py의
  기존 `_read_qwen_values`(배치 실패시 개별·집중 재판독)를 그대로 재사용.
- `correction_dataset.py`: 콜아웃 점을 등록된 sheet_bbox/scan_bbox로
  스캔 좌표에 투영해 가장 가까운 스캔 실측점과 매칭, diff를 계산한다.

### 발견한 버그 — 배포된 백엔드가 구버전 VLM 리더를 쓰고 있었다

콜아웃을 처음 읽었을 때 17개 중 3개만 판독됐다. 원인을 파고드니
Downloads 배포본의 `deviation_extraction/vlm_reader.py`가 **개별
재판독·이진화 재시도(`read_value_focused`) 로직이 아예 없는 구버전**
이었다(git 저장소 main_clone 에는 있음 — 커밋 이력 확인, 그냥 한 번도
동기화 안 된 것). `config.py`, `label_detector.py`, `point_extractor.py`
도 같이 밀려 있었다. 4개 파일을 동기화하니 17/17 전부 판독됐다.

이건 스캔 라벨 판독(P-01..) 에도 영향을 줬을 수 있다 — 이번에 우연히
`correction_dataset.py` 가 `/api/analyze` 를 직접 호출하면서 드러났다.
평소 UI 사용 흐름에서는 못 알아챘을 만한 버그였다.

### 짝 확인 결과 (실측)

| 품번 | 판정 | 비고 |
|---|---|---|
| 64XX2 | 경고 | 부호 분포 반대 — `sheet_reference.py` 에 이미 있던 2026-08-24 경고와 일치 |
| 67XX6 | 경고 | 부호 분포 반대 |

단위로 이상치를 걸러야 한다**는 뜻이다.

총 27개 diff 행 -> `ml_data/correction_diff_dataset.csv`
(짝 확인 결과는 `ml_data/correction_diff_pairing.json`)

### 남은 문제

- 71XX2는 콜아웃 15개 중 2개만 매칭됐다(다른 두 부품은 9/9, 16/17).
  areas 로 등록된 부품의 bbox 투영이 line 부품과 다르게 어긋나는지
  확인 필요.
- 64XX2 에서 같은 스캔점(P-31)에 서로 다른 콜아웃 두 개가 매칭된 사례가
  있다(-0.5 와 0.0) — 콜아웃 검출이나 VLM 판독 중 하나가 오탐일 수
  있다. `match_distance_px` 로 걸러낼 수 있게 CSV에 남겨뒀다.
- scan_value=-10.0 처럼 튀는 값도 보인다 — 스캔 쪽 VLM 오판독 가능성.
  아직 자동 이상치 제거는 안 넣었다.

## 새 사례가 들어오면 할 일 (순서)

1. `my_lab/` 4단계를 새 부품 스캔에 대해 돌려 `zero_points.json`,
   `scan_point_loops.json` 생성
2. `zero_points_data/<품번>.json` 로 복사
3. `python -m zero_line_detection.register_sheet --scan ... --sheet ...`
   로 보정시트 정답 등록 (파일명에 공백·오탈자 없는지 먼저 확인 — 71XX2
   에서 이걸로 한 번 막혔었다)
4. `ml_dataset.py` 의 `CASES` 리스트에 부품 추가
5. `python -m zero_line_detection.ml_dataset` → `train_zero_classifier`
   재실행, `MIN_PARTS_TO_TRUST` 넘었는지 확인
